### 1A. Controlled fault injection
Add `--fault <name>` to `run` and `suite` (repeatable). Faults are applied **in memory / via Playwright request
interception only**, never by editing files under `cases/`. Every result records `faults_injected: [...]`, and the suite
summary shows them. Without `--fault`, behavior is unchanged.

| Fault | Mechanism | Designed outcome (record as `outcome_as_designed`) |
| --- | --- | --- |
| `broken-locator:<target>` | Remove that target from the in-memory human locators. Use a **temporary per-run locator cache** so the heal really happens (not a cache hit) | Action heal → `locator_source: healed`, case PASSED |
| `blank-tiles` | Abort map tile requests (the OSM tile hosts) | Vision BLOCKED (`VISION_INCONCLUSIVE`) at step 4, step 5 still runs, case BLOCKED |
| `directions-503` | Fulfill `GET /directions` with HTTP 503 | Step 2 BLOCKED, reason contains `GET /directions → 503`, later steps NOT_RUN |
| `vision-click:<target>` | Disable the human locator **and** healing for that action target, forcing the vision fallback (1B) | Vision click → `locator_source: vision`, case PASSED |

### 1B. One vision operation fallback (click only)
- Trigger: an action of type **click** whose target can't be resolved by human locator → cache → heal
  (or is forced by `vision-click`). Never for fill/select/press, never for checks.
- Only for targets that declare an **effect target** in `locators.json`, e.g.
  `"layers control": {..., "vision_click_effect": "map layers panel"}`, where the effect target must have a human locator.
  Without a declared effect, no vision click is attempted (BLOCKED as before).
- Request: a full-viewport PNG plus the target's **vocabulary description** (no expected results, no plan values) to the configured
  vision provider. Schema: `found` (bool), `x`, `y` (pixel coordinates in the supplied image), `confidence`, `summary`.
  Python rejects coordinates outside the image. Keep the screenshot at the viewport size (1280×800) and check the provider's
  docs on server-side image resizing, so the coordinates map 1:1 (record the image size used).
- Python: `found` and `confidence ≥ vision_click.min_confidence` (a new required value in `locators.json` or a small config,
  **0.90**) → `page.mouse.click(x, y)` → **verify the effect deterministically**: the effect target becomes visible through
  the human locator. No effect → BLOCKED `VISION_CLICK_NO_EFFECT`. **One attempt; no retry.**
- Evidence: request/response/decision JSON (reusing the vision evidence style and safe error codes), the screenshot, and a
  second copy with the click point marked. The result entry: `locator_source: vision`, coordinates, confidence, summary.
- Why no calibration set is needed here: a wrong click can't produce a PASS, because the effect check decides. Say this
  in the README; record attempts/successes in the summary as observed data only.
- Tests (fake provider): success → effect seen → PASSED; `found=false` → BLOCKED; low confidence → BLOCKED without a click;
  click with no effect → `VISION_CLICK_NO_EFFECT`; out-of-bounds coordinates rejected; a check target never uses the fallback.

## Part 2: Clef comparison (Day 4 rest), rewritten 2026-10-15 after checking the official docs

### 2.0 Facts (verified by the reviewer from official OpenRouter pages)
- Model `cloudflare/clef` (27B multimodal **decision model**, not a chat model): https://openrouter.ai/cloudflare/clef
  The reviewer's earlier "not found" came from the chat/text `/api/v1/models` list, which doesn't include decision models.
- Endpoint: `POST https://openrouter.ai/api/alpha/decisions`, header `Authorization: Bearer $OPENROUTER_API_KEY`.
  **Never use Chat Completions for Clef.** Note the `alpha` path: treat any shape change as a `VISION_*` error, not a silent pass.
- Request (guide: https://openrouter.ai/docs/guides/community/multimodal-decisions):
  `{"model": "cloudflare/clef", "state": [<plain text strings>, {"type":"image_url","image_url":{"url":"data:image/jpeg;base64,..."}}],
    "questions": {"<name>": {"type":"choice","instructions":"...","criteria":{"opt_a":null,"opt_b":null}}, "<name2>": {"type":"noul","instructions":"..."}}}`
  Text items are plain strings (not `{type:text}`). Images go in the **top-level** `state` array. At most **4 images**.
- Response: `answers.<name>` = `{"type":"choice","choice":"opt_a","probabilities":{...},"confidence":0.95}` (or `noul` with a number),
  plus `usage` (input_tokens, cost), `provider` and `id`. Clef returns **calibrated probabilities for every option** and generates no text.
- Limits: keep each image **under ~300 KB before base64** (otherwise HTTP 413). Text in `state` is truncated after ~2,000
  tokens without an error. Clef can't return coordinates, so **the Part 1 vision click fallback stays on Claude** (Clef → `VISION_CONFIG`).

### 2.1 Step 1: text-only smoke test (the user's request)
A tiny script or command (e.g. `python -m test_agent clef-smoke`) sends one text-only Decisions request (e.g. state
`["The traffic light is red."]`, one `choice` question with criteria red/green/unclear) and prints the chosen option,
probabilities, provider and usage. The key comes from `.env` (`OPENROUTER_API_KEY`) and is never printed. Paste the output in the handoff.
Don't continue if this fails; report the HTTP status/code.

### 2.2 Step 2: Clef provider in the existing architecture
- A new `ClefDecisions` provider in `verification/vision_providers.py`, selected by `VISION_PROVIDER=clef` (`VISION_MODEL=cloudflare/clef`).
  It implements the same provider interface; `decide()` stays the only place where PASS/FAILED/BLOCKED is decided.
- **Image preprocessing (Clef only, deterministic):** convert the map PNG to JPEG (or WebP) at a fixed quality, and if needed
  downscale to a fixed max width, until it is < 300 KB. Record the format, quality, size and dimensions, and the hash of the bytes
  sent. Pillow is an acceptable new dependency. The frozen PNGs stay unchanged.
- **Save the compressed images for human inspection** (user decision): write the exact bytes sent to Clef as
  `cases/osm/vision_calibration*/compressed/<name>.jpg` (frozen and hashed like the PNGs, committed with the task), and the per-run
  copy into the run's vision evidence folder. Use mild settings: start at JPEG quality 90 and step down in fixed steps, then downscale only if
  still ≥ 300 KB. Record the final setting per image. In the handoff, list the size and quality per image and ask the user to check that
  the labels are still judgeable by a human on the JPEGs (e.g. "Potsdam" readable). If a label isn't judgeable after compression, report
  it; don't change the label silently.
- Safe errors: reuse `VisionError` codes (`HTTP` with status only, e.g. 400/413/422/429/5xx; `TIMEOUT`; `NETWORK`;
  `SCHEMA` when `answers`/`choice`/`probabilities` are missing or contain an unknown option). No retries. No raw error bodies in logs.

### 2.3 Questions: keep the blind-observation lesson (important)
The user asked for decision choices like **SUCCESS / FAILURE / UNCLEAR**. The application still gets exactly that, but the
**model should not be asked** "is this the route from Hamburg to Berlin? SUCCESS/FAILURE". Calibration showed that asking the
model to judge a stated requirement causes false PASSes (anchoring: Claude passed Potsdam and the reversed route 5/5).
So implement two question sets and measure both:
- **Variant A, blind (default, used in production):** the state has the image plus a neutral instruction only; no expected cities.
  - `start_city` (choice): "Which labelled city is the GREEN start marker on?" Criteria = a **fixed suite-level candidate list**
    (e.g. `cases/osm/vision_cities.json`: Hamburg, Berlin, Munich/München, Potsdam, Bremen, Leipzig, Rostock, Bernau, …) plus
    `other` and `unclear`. The list is the same for every case, so it doesn't reveal the expected answer.
  - `end_city` (choice): the same, for the RED end marker.
  - `route_line` (choice): continuous / broken / none / unclear.
  - Python maps these to the decision: **SUCCESS** = start = origin, end = destination (aliases allowed), line continuous, each
    chosen option's probability ≥ `min_confidence` (0.90) → PASSED. **FAILURE** = a confident (≥ 0.90) different city
    (including `other`) or `broken` → FAILED. **UNCLEAR** = anything else (`unclear`, `none`, a probability below the threshold) → BLOCKED.
  - Return the decision **and** all probabilities in `CheckResult.actual` (per question: choice, probabilities, confidence), and in
    the reason line, e.g. `Clef SUCCESS: start Hamburg 0.97, end Berlin 0.95, line continuous 0.99 (min 0.90)`.
- **Variant B, direct (OPTIONAL, user decision 2026-10-15: do it only if time remains after everything else; calibration only, never production):** the state includes the requirement text, with one choice
  question `route_matches` → SUCCESS / FAILURE / UNCLEAR, mapped the same way (the chosen probability ≥ 0.90 is required for PASS/FAIL).
  This measures whether Clef also anchors. It's report data only; skipping it doesn't block acceptance.
- `decide()` gets a Clef path (or a small adapter that turns Clef answers into the same internal observation). Keep it pure, so
  calibration replay at other thresholds still works.

### 2.4 Calibration and comparison
- Run `calibrate run` on **both frozen sets**, `--runs 5`, threshold 0.90, for:
  1. **Clef, Variant A** (required);
  2. **Claude on the same compressed JPEGs** (required, user decision): the same blind prompt/schema as the existing Claude reports, but
     fed the exact JPEG bytes Clef received. This separates "compression lost information" from "Clef is weaker";
  3. Clef, Variant B (optional, see 2.3).
  Clef calls are cheap and fast (about $0.042/M input tokens, ~0.3 s P50 on the model page).
- Clef's probabilities are calibrated, so repeated runs may be identical. Report that if so; it's a useful finding about repeatability.
- Comparison table, one row per column: **Claude PNG** (existing reports `calibration-20261015T072050441635Z`, `calibration-20261015T072233121599Z`)
  vs **Claude JPEG** vs **Clef A (JPEG)** (vs Clef B if run):
  false PASS, correct-image PASS, clear-mismatch FAILED, BLOCKED rate, error codes, latency p50/p95, cost per call. Evaluate against the same acceptance bar.
- Interpretation line in the handoff: if Claude JPEG ≈ Claude PNG, compression is not the cause of any Clef weakness; if Claude JPEG is clearly
  worse, report compression as the likely cause and propose a gentler setting (higher quality / WebP) for the user to decide.
- **The user decides which provider to use** from this table. Both stay selectable via `.env` (`VISION_PROVIDER=anthropic|clef`); don't remove either.
